# 滴答清单日程创建

将用户给出的工作整理为简短、具体、可执行的滴答任务。用户已要求创建时，信息齐备即可写入；只为影响归属、排期或任务含义的关键缺口提问。

## 1. 读取账户与任务上下文

使用「滴答清单: To-Do List & Calendar」连接器。当前工具名前缀为 `mcp__codex_apps__to_do_list___calendar__to_do_list_calendar_`；调用参数以宿主实际提供的工具定义为准。

- 读取 `list_projects`、`list_project_groups`、`list_tags` 和 `get_user_preference`，获得真实清单、文件夹、标签及时区。清单查询需包含收集箱，必要时完成分页。
- 从用户描述及已知上下文提取工作内容、最终目的、交付、项目线索、日期和关联任务。描述未提供的成果或研究结论不补造。
- API 的 **project 是清单**，`projectId` 是清单 ID；科研项目名称按下文白名单识别。账户对象 ID 在本次调用中解析，不写死进技能。

## 2. 选择文件夹和清单

用户明确指定目标位置时遵从指定；自动归类采用**工作类型优先**，依据主要工作及交付选择：

| 文件夹 | 清单 | 适用内容 |
| --- | --- | --- |
| 分析工作 | 科研项目的规范名称 | 项目数据整理、具体分析、项目结果或报告整理 |
| 分析依赖 | 环境 | 软件安装、运行环境搭建与维护 |
| 分析依赖 | 方法 | 方法调研、复现、评估与工具使用准备 |
| 分析依赖 | 数据库 | 参考数据库获取、构建、整理与维护 |
| 文献学习 | 初读筛选 | 快速阅读、相关性判断、决定是否深入阅读 |
| 文献学习 | 精读 | 已明确要求深入阅读、逐图梳理或系统理解论文 |

环境、方法、数据库和论文阅读即使服务某个项目，也优先进入相应类型清单，正文必要时注明关联项目。以读懂或筛选论文为主要交付时选择文献学习；以方法复现、评估为主要交付时选择分析依赖／方法。泛称“读文献”且没有精读要求时，默认初读筛选并简要说明。

### 远端项目清单作为白名单

项目白名单的唯一来源是**当前滴答账户中“分析工作”文件夹下，以规范项目名命名的项目清单**。每次使用技能时重新读取，供连接同一账户的不同机器共享；技能文件和本地缓存均不维护项目成员表或别名表。

1. 从 `list_project_groups` 确定“分析工作”文件夹的真实 `id`；同名文件夹不唯一时先询问。再从 `list_projects` 选择 `groupId` 对应、未关闭（`closed` 不为 `true`）的任务清单（`kind=TASK`）。排除收集箱、其他文件夹的清单，以及与文件夹同名的“分析工作”通用清单。其余项目清单的实际 `name` 是规范项目名，`id` 用于创建任务。
2. 优先采用用户明确的规范项目归属或清单名完整匹配。分析项目标题以某规范名开头，且规范名之后是结束、下划线、连字符或空格时，可识别为该项目；比较可忽略英文大小写，输出保留远端清单的实际写法。前缀匹配得到多个项目时询问，不通过删改字符或相似拼写制造匹配。
3. 例如远端已有 `proj_HMFmmu` 项目清单时，分析项目标题 `proj_HMFmmu_scRNA` 可以归入该清单。`proj_cellAging`、`proj_HMFmmu` 在这里仅是命名示例，不构成远端缺失时的本地白名单兜底。
4. 需要项目归属而未匹配时，询问规范项目名；当前会话已明确确认规范名的可直接复用该确认。若对应清单尚不存在，在用户已授权创建该项目日程的范围内，按需将其创建到“分析工作”文件夹。新清单经返回结果或回读确认后，就成为后续各机器读取的白名单成员，无需修改技能。
5. 远端读取失败时先解决读取问题，不将失败当作空白名单并重建清单。文件夹不存在或确实没有项目清单时，按上一条确认规范名后按需创建；不能从分析项目标题直接猜出科研项目名。

任意别名若既不等于规范项目名，也不保留规范项目名前缀，仅靠清单名称无法持久表达其映射；这类归属可采用当前会话的明确确认，其他会话缺少依据时重新询问。跨机器长期复用优先让分析项目标题保留规范项目名前缀，不为保存别名另建一个项目清单。

### 复用与按需创建

按“文件夹名＋清单名”核对真实对象后复用。实际新建前再次确认目标路径尚不存在，减少其他机器已创建后的重复创建。已有不同父级的同名清单不自动搬迁，旧清单和历史任务保留；同一路径存在多个候选时先消除歧义。

上述分类缺项时，在当前日程确实需要时创建相应文件夹、清单。其他内容只有用户明确表示会持续开展，或上下文明显属于稳定重复类别时，才创建新的清单，必要时创建文件夹；其余进入收集箱。一次性任务不需要为了归类而搭建空层级。

## 3. 添加三维标签并判断优先级

每条日程在以下每个维度选择**一个主标签**，通常共三个；用户另有明确标签要求时再补充。

| 维度 | 规范标签 | 判断依据 |
| --- | --- | --- |
| 四象限 | `紧急且重要`、`重要但不紧急`、`紧急但不重要`、`不重要且不紧急` | 截止、时效和下游阻塞决定紧急性；对最终目的的影响决定重要性 |
| 作用 | `基础`、`优化`、`探索` | 基础：必不可少；优化：有条件实施会改善结果；探索：是否改善结果尚不确定 |
| 交付角色 | `原料`、`过程`、`输出` | 原料：获取资源、整理数据、搭建环境；过程：具体工作执行；输出：整理结果形成报告、PPT 等交付 |

按任务本身对下游的主要交付判断角色；复合任务选择主要作用和角色。排在今天不自动意味着紧急，基础工作或报告输出也不自动意味着高优先级。

读取并复用实际标签，缺失时按需创建个人标签（`name` 与 `label` 使用规范名，`type=1`）。`不紧急但重要` 按同义项理解，新任务统一使用 `重要但不紧急`；不为统一命名而删除、重命名旧标签或批量修改旧任务。

优先级采用四象限作为初始参考：紧急且重要→高 `5`，重要但不紧急→中 `3`，紧急但不重要→低 `1`，不重要且不紧急→无 `0`。再结合用户阐述、实际截止、下游阻塞、作用和交付角色综合调整。调整不机械改变四象限标签；必要时用一句话说明影响判断的理由。

## 4. 安排日期

- 默认全天；用户明确给出具体时刻时按时刻创建。日期优先采用明确要求，再根据任务上下文解析；两者均无法确定时询问日期，不默认今天或创建未排期任务。
- 使用账户时区解析“今天”“明天”等相对日期，并生成该时区对应实际 UTC 偏移的时间戳。账户未返回时区时采用用户明确的时区；本用户当前默认 `Asia/Shanghai`，使用默认值时说明。
- 未写年份时优先使用明确的上下文年份，否则采用当前年份；遇到明显过去日期或跨年含义不清时询问，不默默顺延一年。
- 全天范围包含首尾日期和其中的自然日。单日的 `startDate`、`dueDate` 均为同一天本地零时；多日分别为首日、末日本地零时，`isAllDay=true`，`timeZone` 与 `client_timezone` 一致。
- 例如在 `Asia/Shanghai` 下，2026 年 `10.12–10.14` 编码为 `startDate=2026-10-12T00:00:00+0800`、`dueDate=2026-10-14T00:00:00+0800`，意图覆盖三天；单日 `10.12–10.12` 的两个字段均为 12 日零时。不要按其他日历的结束日排除规则自行增加一天。
- 默认不设置提醒或重复（新建任务 `reminders=[]`，省略重复字段）；用户要求时再配置。结束早于开始等日期冲突在写入前解决。

单日全天保存已在本次会话回读验证，多日客户端展示尚未实测；回读字段只能证明保存结果，不等于已验证客户端视觉表现。

## 5. 编写标题与必要正文

标题通常用一行动作＋对象或交付表达，例如“整理 AT2 分析结果并完成汇报”。正文按需要补充目标、范围、输入、完成标准或关联项目；没有必要补充时省略正文，不套用空模板。

正文默认采用短段落、列表和必要强调。涉及代码、表格替代、图片或关联日程时，读取 [正文格式支持与测试记录](references/format-support.md)，遵循其中的已知兼容范围。

关联其他日程时，通过 `search_task` 或宿主对应搜索工具取得候选，再核对清单、日期和内容，使用返回的真实任务链接。正文可写“前置日程”“后续交付”“参考日程”，关系需由上下文支持；仅添加正文链接不会建立原生任务依赖，也不自动将任务改成子任务。

## 6. 创建、核对并返回结果

1. 先完成必要的日期、归属澄清，形成清单路径、三维标签、优先级、日期、标题及可选正文；再开始账户写入。
2. 按需调用 `create_project_group`、`create_project`（将文件夹返回的 `id` 传入 `group_id`，清单 `kind=TASK`）和 `create_tag`。依次使用真实返回 ID，复用已经完成的步骤。
3. 使用 `create_task` 创建，正文任务采用 `kind=TEXT`、`status=0`；提供目标 `projectId`、日期、时区、标签名称和合法优先级值。仅发送当前任务需要的字段。
4. 保存返回的任务 ID，通过 `get_task_by_id` 或对应读取工具核对标题、清单、日期范围、全天状态、标签、优先级和正文要点。需要更正时只修正本次创建的对象，使用最新版本信息并重新核验。
5. 创建返回不明确或发生超时时，先按标题、清单、日期及正文关键内容查找是否已成功；确实未创建才重试。存在多个无法区分的候选时先询问，不盲目重复创建。失败时说明已完成的部分和剩余错误。
6. 通过搜索或读取结果取得任务的真实 URL；若按标题搜索，按本次返回的任务 ID 选择链接。简洁返回日程链接、完整清单路径、日期、三维标签、优先级及必要假设。保存成功与客户端渲染验证分别报告。
