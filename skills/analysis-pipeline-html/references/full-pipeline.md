# 模式 2：从项目原始数据到目标单元

仅在用户选择完整流程时读取。这里解决的是“当前结论依赖哪些上游步骤”，不是罗列项目历史。

## 追溯实际使用的数据流

从目标单元的当前有效结果向上追踪。对每个关键输入，核对来源文件、生产它的单元或外部流程、使用版本，以及它在当前分析中的用途。可先用任务元数据的 `upstream` 寻找候选，再用实际运行记录和脚本的输入路径确认。

依赖按实际作用处理：

| 作用 | 正文处理 |
| --- | --- |
| 产生当前分析使用的计数、质控集合、注释、模型、分组或坐标 | 纳入必要的上游处理步骤，说明输入、关键转换、实际输出和局限。 |
| 提供当前结论实际使用的比较或支持证据 | 作为支持分支纳入，并说明其与主流程的关系；不冒充计算前置步骤。 |
| 只复用工具代码、环境或通用方法 | 记录代码/环境来源，不展开该工具曾运行过的全部任务。 |
| 仅在摘要中提到，当前结果未使用 | 不因存在引用就纳入完整流程。 |

同一上游产物被多个单元使用时，只解释一次，在流程图中画出分支。若多个单元重复实施同类方法，保留它们不同的输入、参数或用途，只有这些差异不会影响判断时才合并说明。

## 确定数据起点

“项目原始数据”按实际研究输入解释，不预设一定是 FASTQ，也不把首次出现的派生对象直接称为原始数据。

- 原始文件和处理记录齐全：从该数据层开始，按执行事实连接至当前分析。
- 已知由服务商或外部流程完成上游，但本地只保留处理产物：说明原始数据类型、已知软件/参数和输入来源；缺失的文件或参数写明“未提供/未记录”。不能把未核实的上游写成已在本项目完成。
- 公共参考或外部队列：说明其来源、研究背景和进入本项目后的实际处理。除非当前任务依赖其原始处理细节，否则不重建原论文的全部分析。
- 多个原始数据来源：在总览中保留多个入口，标明首次汇合处及关键连接标识。

读取项目数据清单和元数据来定位入口，避免递归扫描大型原始数据目录。归档依赖按项目规则按需读取，不为出报告迁移或恢复整个归档。

## 组织完整流程

先得到由真实产物连接的步骤图，再按依赖顺序写正文。每步标注所属单元，关键连线说明传递的内容，例如“过滤后的计数”“细胞注释”或“区域分组”，而不只有箭头。

对照以下问题确认范围完整：

1. 从所声明的数据起点出发，能否解释目标结论使用的数据、分组和关键模型如何得到？
2. 共享依赖是否只讲一次，支持分支是否与计算依赖区分？
3. 上游替换、参考缺口或失败是否会改变当前结论，相关限制是否随步骤传递？
4. 流程终点是否确为用户指定的分析单元，而不是扩展到项目其他下游任务？

元数据依赖出现环时，回到实际文件版本核对，区分历史迭代与真实数据流；无法消解的连接明确标注。路径或版本冲突未解决时，只陈述可核实事实，标记受影响步骤，继续解释不受影响的部分。

## 与模式 1 的最小对照

假设目标 C 使用上游 B 生成的注释，B 使用 A 的过滤计数，A 来自原始矩阵；另有 D 只提供可复用绘图代码。

- 模式 1：用一个输入概览说明原始数据背景和 B 注释来源，详细步骤仅讲 C。
- 模式 2：按“原始矩阵 → A 质控 → B 注释 → C 分析”解释；D 只作为代码来源，不展开其科学分析。

这是范围判断示例，不是对实际任务依赖的预设。
