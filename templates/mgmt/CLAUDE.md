# 管理侧（`mgmt/`）——定方向、读结论、写方案

> 规范根：`<CANONICAL_ROOT>`。本侧规则自足，无需读 `analysis/CLAUDE.md` 或 `explore/CLAUDE.md`。
> **只放文档**：不跑重计算、不落大文件、不建分析目录。管理侧要能被整体读进上下文，这是它存在的理由。

## 文件分工

| 文件 | 放什么 |
|---|---|
| `PROJECT.md` | 研究背景 / 科学问题 / 目标。最上游的锚，改动应当少 |
| `RESOURCES.md` | 已有数据：绝对路径 / 规模 / 内容 / 命名键 / 已知坑。**只写数据不写方法** |
| `PLAN.md` | 任务链（含依赖）+ 每节点进度。三态 `待做` / `在跑` / `已出结论` + 一句话现状。**只挂 `A<idx>`，不挂 `E<idx>`** |
| `FINDINGS.md` | 已立住的结论与关键决定。**只增不改**，每条带绝对日期 + 依据的 `A<idx>`（或用户点名收进来的 `E<idx>`） |
| `plans/` | 按需写的分析方案，一个 task 或一个问题一个文件。无强制模板 |

## 看分析结果：先扫 abstract，再展开 SUMMARY

**开工先跑 `bash <CANONICAL_ROOT>/bin/abstracts.sh`** —— 一次拿到两侧所有单元的一句话摘要与上游关系（通常几十行）。
据此挑出这次真正要动的那几个 A，再展开它们的 `analysis/A*/SUMMARY.md`（五节固定标题——结论 / 关键数字 / 产物 / as-run / 坑）。
**不通读全部 SUMMARY**；也**不读** `scripts/` `logs/` 与结果表原文，除非在追一个具体的可疑数字（下潜要在返回里说明理由）。
要横向看某一维度，就 grep 各 SUMMARY 的同名节。

**`explore/` 只在 abstract 层可见。** 你能扫到 E 的摘要——好处是知道旁边在跑什么、不重复派活、能向用户提议「E0x 值得开个 A 复核」；
但**展开某个 `explore/E*/SUMMARY.md` 仍须用户点名**。摘要可见 ≠ 结论回流：`E<idx>` 不进任务表、结论不自动进账本，这条不因为能扫到摘要而松动。
用户点名「把 E0x 的结论记进账本」时才去读那一个 SUMMARY，并在依据列写明是 E。要让一个探索结论真正立住，正路是请用户在 `analysis/` 开一个 A 重做。

## 写方案（`plans/`）

写清四样就够：**目标一句话 / 输入路径 / 方法与关键参数 / 期望产物**。
执行拓扑、逐步断言、路径白名单**不要写**——那些属于 `analysis/` 的脚本，写进方案只会让方案长出接缝。

带可证伪假设时**可以**（不强制）再加：待检验命题 / 判据与阈值 / 统计方法与多重检验 / 阴性怎么写。
写完 `git commit` 再开跑，该时间戳即「计划先于结果」的证据；省掉也行，代价是日后无法区分「事先预测」与「看完数据才提」。

## 方案不自动进入分析侧

方案写完 ≠ 可以开跑。分析侧只听用户的指令：用户可点名「按 `mgmt/plans/xxx.md` 跑」，也可不点名直接口述。
**最多提议一次，不代替用户下令**；提议时须同时说明代价（机时 / 能否重跑 / 挡住了什么）。

## 结论进 FINDINGS

判「这个结论立住了」是管理侧的活。缺把握时可请用户点名派 `reviewer` 审那个 A 或 E（只判结论是否被数据支持）。
审核不是闸门——它只在用户点名时发生。
